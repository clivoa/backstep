# 09 — Street Fighter Alpha 3

## Por que um jogo de verdade

A arena prova que o motor de rollback funciona. Ela não prova que funciona em uma
simulação que ninguém escreveu para isso.

O SFA3 sob FBNeo é opaco: nenhum campo é conhecido, o estado tem megabytes, e a
única forma de salvá-lo é `retro_serialize`. Se o mesmo `RollbackSession` dirige
os dois, a fronteira da trait `Simulation` está no lugar certo.

## O core

### Sobre o commit pinado

O enunciado do laboratório pina
`finalburnneo/FBNeo@f1c3545fcdfca4dd5fcf9c1baaac6bba143785f8`.

**Essa árvore não contém um port libretro.** Verificado diretamente: o commit
existe, é do dia 17/08/2026, e `src/burner/` nele tem `sdl`, `sdl2`, `win32`,
`qt`, `pi`, `psp` e `macos` — mas nenhum `libretro`. O upstream do FBNeo não
hospeda o port libretro; ele é mantido no fork `libretro/FBNeo`, cujo master
naquele momento (`0332bb983c8f8a3e9b61cb79ade30f97a5032535`, de 16/08/2026)
ainda não tinha incorporado o commit citado.

Ou seja: compilar o core libretro *exatamente naquele commit* é impossível.

A resolução preserva a intenção — "core oficial, pinado de forma reprodutível" —
sem fingir que o pin do enunciado funcionou:

- o container compila `libretro/FBNeo@0332bb983c8f8a3e9b61cb79ade30f97a5032535`,
  fixado exatamente;
- **os dois SHAs** são gravados no arquivo de proveniência exportado, para a
  discrepância continuar auditável:

```
libretro_fork_commit=0332bb983c8f8a3e9b61cb79ade30f97a5032535
spec_commit=f1c3545fcdfca4dd5fcf9c1baaac6bba143785f8
```

Se o commit do enunciado for eventualmente mesclado no fork libretro, basta
mudar `FBNEO_LIBRETRO_COMMIT` — em `docker/fbneo/Dockerfile` e em
`ops/scripts/build-fbneo.sh` — para o merge correspondente.

### Compilar

```bash
just build-core
```

O container é Ubuntu 24.04, faz um `git fetch --depth 1` do commit exato (sem
histórico, sem outras refs) e roda `make -C src/burner/libretro`. A saída vai
para `cores/`:

```
cores/fbneo_libretro.so           ~90 MB
cores/fbneo_libretro.so.sha256
cores/fbneo-commit.txt
```

O SHA-256 é o que os dois peers comparam no handshake.

## A ROM

**Você fornece.** Nada relacionado a ROM é versionado, redistribuído ou incluído
em qualquer artefato deste repositório.

Os dois peers precisam de arquivos **idênticos**: o handshake compara SHA-256 e
recusa com "ROM hash mismatch" antes de a partida começar. Uma revisão diferente
de ROM é um jogo diferente e desincronizaria em segundos.

### O set precisa incluir a chave CPS-2

O FBNeo espera **21 arquivos** para o romset `sfa3`, e o vigésimo primeiro é
`sfa3.key` — 20 bytes, CRC `54fa39c6`, a chave de descriptografia CPS-2.

Sets mais antigos, de antes de o CPS-2 ser decifrado, têm os 20 arquivos de ROM
corretos e **não** têm a chave. O sintoma é peculiar e vale reconhecer:

```
Error: loading ROM "/caminho/sfa3.zip"
Caused by: core reports a serialize size of zero, so no game is actually running.
```

O FBNeo **retorna sucesso** de `retro_load_game` mesmo com um romset inutilizável
— ele desenha o motivo na tela emulada, via a própria UI, em vez de contar ao
frontend. Do lado de cá, o único sinal é `retro_serialize_size()` devolver zero.

Para conferir o que o core acha do seu arquivo:

```bash
just inspect-core rom=/caminho/sfa3.zip
```

E para comparar arquivo por arquivo, a definição do romset está em
`src/burn/drv/capcom/d_cps2.cpp`, em `Sfa3RomDesc[]`, com nome, tamanho e CRC de
cada entrada. Um set correto bate nos 21.

`just aws-up sim=sfa3 rom=...` sobe a ROM para o bucket privado e criptografado,
que tem lifecycle de 7 dias e é apagado explicitamente por `just aws-down`.

## Determinismo do ambiente

O emulador é determinístico. O ambiente ao redor dele não é automaticamente.

### NVRAM

FBNeo lê NVRAM e configurações por jogo do diretório de sistema. Um arquivo
antigo em um dos lados é desync no frame zero, antes de qualquer input — e um
desync antes do primeiro input é particularmente confuso de diagnosticar, porque
os inputs estão obviamente corretos.

`host::set_directories` existe para isso, e os dois peers apontam para um
diretório limpo (`artifacts/system` localmente, `/opt/rollback/artifacts/system`
na EC2).

### Opções do core

Fixadas em `PINNED_CORE_OPTIONS` — a tabela e o motivo de cada uma estão em
[05 — Determinismo](05-determinismo.md). A mais importante é `fbneo-frameskip=0`:
frameskip faria `retro_run` avançar um número variável de frames, e todo o
rollback assume exatamente um.

## Boot determinístico

### Por que macros temporizadas e não leitura de memória

A forma óbvia de automatizar um boot é ler a RAM do jogo: observar um byte de
"modo", esperar o valor que significa "seleção de personagem", e apertar. É
rápido, robusto — e proibido aqui, de propósito:

- offsets de memória são específicos de versão e região, então a automação
  quebraria silenciosamente numa revisão diferente de ROM **enquanto o handshake
  continua dizendo que os hashes batem**;
- ler RAM via `retro_get_memory_data` não é parte do que o rollback precisa, e
  criar essa dependência faz o laboratório deixar de demonstrar que rollback
  funciona numa simulação *opaca*.

Então o script é puramente temporal: segure um botão por N frames, espere M, siga.
Isso só é válido **porque o emulador é determinístico** — o mesmo script a partir
do mesmo reset chega na mesma tela no mesmo frame, nos dois peers. Que é
exatamente a premissa do laboratório.

### O script

```
420 frames  esperar os logos                        (7 s)
 2 ×        ficha: segurar 6, esperar 24
 2 ×        start: segurar 6, esperar 24
180 frames  intro da seleção de personagem          (3 s)
 N ×        direita: segurar 6, esperar 12          (N = slot do personagem)
 2 ×        confirmar: segurar 6, esperar 24        (personagem, depois ISM)
300 frames  intro do round                          (5 s)
```

Total: ~19 s antes de o controle passar aos jogadores. Cada etapa espera bem mais
do que a animação precisa. Um boot dois segundos mais lento não custa nada; um
boot que aperta um frame cedo demais dessincroniza o estado do menu entre os
peers e a partida começa com personagens diferentes.

P1 fica no slot 0, P2 anda 3 posições à direita. Os dois lados rodam **as duas**
macros nos mesmos frames absolutos, então fazem inputs de menu idênticos mesmo
cada um só controlando um jogador.

Durante o boot os inputs do humano são **ignorados**, para que um aperto acidental
não mude a seleção em apenas um dos peers.

### O bot do P2

Depois do boot, o P2 toca um repertório fixo de macros escolhido por um RNG
semeado: andar e dar jab, recuar e defender abaixado, pular entrando, meia-lua
para frente com soco, cutucar abaixado, e ficar parado.

Ele **não lê nada do jogo** — não pode, sem offsets de ROM. Ao contrário do bot
da arena, que reage ao estado, este toca de olhos fechados. É suficiente: o
objetivo dele é gerar variação de input para o experimento de rollback, não jogar
bem.

"Ficar parado" está no repertório de propósito: o jogo neutro também importa, e um
bot que nunca para torna a previsão irrealisticamente difícil.

## Rodar

Local (dois processos):

```bash
export ROLLBACK_SESSION_KEY=$(head -c 32 /dev/urandom | od -An -tx1 | tr -d ' \n')

cargo run --release -p rollback-bot -- --sim sfa3 --player p2 \
  --bind 127.0.0.1:7000 --profile combined --duration 180 \
  --core cores/fbneo_libretro.so --rom /caminho/sfa3.zip \
  --metrics 127.0.0.1:9899

cargo run --release -p rollback-client -- --sim sfa3 \
  --peer 127.0.0.1:7000 --profile combined \
  --core cores/fbneo_libretro.so --rom /caminho/sfa3.zip
```

Contra a AWS:

```bash
just aws-up sim=sfa3 rom=/caminho/sfa3.zip
just play   sim=sfa3 rom=/caminho/sfa3.zip
just collect
just aws-down
```

## Critérios de aceitação

1. **Boot determinístico** — os dois peers chegam à mesma tela no mesmo frame e
   selecionam os mesmos personagens.
2. **P1 humano** — o controle passa ao jogador quando o script termina.
3. **P2 atuando** — o FSM produz inputs contínuos.
4. **Rollback observável** — sob `--profile combined`, o overlay mostra frames
   amarelos e vermelhos, e os contadores sobem.
5. **Checksums convergentes** — `checksums_compared` sobe nos dois peers e
   `desync` fica em 0 pela sessão inteira.

## CI sem ROM

`fake-libretro-core` é um `cdylib` Rust de verdade que implementa a mesma ABI
libretro: um "jogo" trivial (dois pontos numa linha de 64 pixels, estado de 32
bytes) mas sensível a ordem, para que um `retro_run` a mais ou a menos apareça no
checksum.

`crates/rollback-libretro/tests/fake_core_ffi.rs` carrega esse core por `dlopen`
e exercita o caminho FFI inteiro — environment callback, `retro_run`,
`retro_serialize`/`retro_unserialize`, vídeo, áudio, descarte de saída em
re-simulação — incluindo uma sessão de rollback completa que converge no mesmo
estado de uma execução limpa.

Ou seja: CI testa tudo do host libretro exceto o emulador em si, numa máquina que
nunca viu uma ROM protegida.

## Custo de CPU

O `retro_serialize` do SFA3 produz alguns megabytes por frame. O host guarda o
checksum do último snapshot em cache (`cached_checksum`), porque a sessão chama
`save_state` e `checksum` em sequência e serializar duas vezes por frame
consumiria a maior parte do orçamento.

Vale medir no dashboard: **Custo de execução → Tempo por frame**. Se
`advance + save_state` passar de ~8 ms, o pior caso de rollback (8 re-simulações)
não cabe mais nos 16,7 ms, e é hora de `t3.medium`.
